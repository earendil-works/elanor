# Composer

The field where a person writes a chat message: the prompt with chips, buttons inside the frame, and rows above and below for notices and settings. For a plain multi-line field, use [Text area](/components/text-area/).

<Demo example="./examples/demo.tsx" />

The example is a conversation view with a whole composer: suggestions for files and commands, chips, uploads, a drop zone, recall of sent messages, and a footer. The sections below quote it; a section has its own example only where the whole one can't show it, such as a narrow composer.

## Usage

```tsx
import {Composer} from '@earendil-works/elanor-react';

<Composer.Root>
  <Composer.Panel>
    <Composer.Header />
    <Composer.Field>
      <Composer.Prompt />
      <Composer.Controls>
        <Composer.Attach />
        <Composer.Submit />
        <Composer.Stop />
      </Composer.Controls>
    </Composer.Field>
    <Composer.Footer />
  </Composer.Panel>
  <Composer.Suggestions>
    <Composer.SuggestionStatus />
    <Composer.SuggestionPortal>
      <Composer.SuggestionPositioner>
        <Composer.SuggestionPopup>
          <Composer.SuggestionList>
            <Composer.SuggestionItem />
          </Composer.SuggestionList>
          <Composer.SuggestionEmpty />
        </Composer.SuggestionPopup>
      </Composer.SuggestionPositioner>
    </Composer.SuggestionPortal>
  </Composer.Suggestions>
</Composer.Root>;
```

- **Root** holds the prompt's value, its undo history and its settings. It renders no element: the other parts and the hooks work anywhere inside it, also outside Panel and in portals, and the parts and the hooks throw outside it. `toText` is required: it gives the text that is copied, submitted with a form, and sent.
- **Panel** renders a `div` around the rows and fills its container's width. For a form, see [In a form](#in-a-form).
- **Header** is the row above the field, for notices, errors, and the message being replied to.
- **Field** is the frame, which looks like one text field holding the prompt, with its chips, and the buttons. It has no focus ring; the caret shows the focus, and the field keeps its fill while a person writes, darkening only under the pointer or a press. Pressing anything in it other than the text keeps the focus where it is, so a phone's keyboard stays up. Field also works without a Panel.
- **Prompt** is the text. `maxRows` sets how many lines of text the prompt grows to before it scrolls (10 by default; at most 40% of the viewport, so it stays above a phone's keyboard). Name it with `aria-label` or a `Field.Label`.
- **Controls** is the row of buttons inside the field, in DOM order; place them as you like. Use [Icon buttons](/components/icon-button/) with `density="default"`. **Attach**, **Submit** and **Stop** are icon buttons for attaching files, sending and stopping a reply.
- **Footer** is the row below the field, for your own controls and figures, such as a model picker and the context used. It's layout only: it sets no text style, so the size of its text is yours to choose.
- **Suggestions** shows a list at a trigger being typed, such as `@` for files. It renders no element; **SuggestionPortal** renders into the page's body, or a `container`, and **SuggestionPositioner** places **SuggestionPopup** at the trigger, which holds the **SuggestionList** of **SuggestionItem**s and **SuggestionEmpty** for when nothing matches. **SuggestionStatus** tells screen readers about the list. See [Suggestions](#suggestions).

The containers take any number of children, and an empty one takes no room. Panel is a size container named `composer`, so your own styles can follow the composer's width with `@container composer (…)`. Its public custom properties are `--composer-hang` and `--composer-footer-inset`, which you set, and `--composer-text-inset`, which you read; see [Footer](#footer) and [Alignment](#alignment). If you load code separately, such as plugins, share one copy of this package with it: the hooks find Root through React context.

## Sending

Enter and Alt+Enter call Root's `onSubmit`, and so does Submit. The details carry the event, so Alt+Enter can do something else, such as queue a follow-up. Shift+Enter adds a line. Set `submitShortcut="mod-enter"` to send with Cmd+Enter or Ctrl+Enter instead; then Enter adds a line. Nothing is sent while an input method is composing, or while [suggestions](#suggestions) show, where Enter picks one. The composer doesn't check whether the prompt is empty: Submit stays enabled, and you decide, for example with `empty` from `Composer.useStatus()`. Some Android keyboards don't report which key was pressed, so there Enter adds a line and Submit sends.

The example checks the message in `onSubmit`, then clears the prompt and its undo history:

```tsx from="./examples/demo.tsx"
// Enter sends without Submit, so check here too.
onSubmit={(message) => {
  if (pending(uploadIdsOf(message)) || !toText(message).trim()) return;
  onSend(message);
  actions.current?.clearHistory();
  setValue([]);
}}
```

To queue a follow-up with Alt+Enter, read the key event from the details:

```tsx
onSubmit={(message, {event}) => {
  if (event instanceof KeyboardEvent && event.altKey) queueFollowUp(message);
  else send(message);
}}
```

Prompt's `onKeyDown` runs before the composer handles a key; call `preventDefault()` to handle it yourself.

## Stop

`Stop` is a button for stopping a reply: stop it in `onClick`. The composer doesn't know whether a reply is running, so render `Submit` or `Stop` yourself. `Composer.useStatus()` gives `empty`, `disabled` and `readOnly`, so you can offer Stop only while nothing new is written. Give each its own `key`: a press meant for Stop then never sends. When the one with the keyboard focus goes, the other takes it. The example shows Stop while a reply runs and the prompt is empty; once a person writes, Send comes back, and Enter on the empty prompt sends nothing, since `onSubmit` skips an empty message:

```tsx from="./examples/demo.tsx"
/** Stop while a reply runs and nothing new is written, so a press meant for Stop never sends. */
function SendOrStop({replying, onStop}: SendOrStopProps) {
  const {empty} = Composer.useStatus();
  return replying && empty ? (
    <Composer.Stop key="stop" onClick={onStop} />
  ) : (
    <SendButton key="send" />
  );
}
```

## Files

`Attach` opens the file picker; set `accept` and `multiple` on it, and `capture` to offer the camera on phones. Root's `onAttach` receives the picked files, and files pasted on the prompt or dropped on the field, with a `reason` of `picker`, `paste` or `drop`. Files are chips in the text, where they are mentioned: in `onAttach`, pass one chip per file, drawn as `Upload › name`, to `details.insert`. `details.insert` always puts a space around what it inserts where the text needs one. `actions.insert` inserts exactly what you pass; set `space: true` for an insert a person made, as the example does for a suggestion pick.

- `details.insert` puts them at `details.at`. Files go in at the caret, after any selected text, or at the end if the prompt was never focused; dropped files go there wherever on the field they are dropped. A paste replaces the selection. After `details.insert`, the caret collapses after the chips.
- They are one undo step, with the paste's or drop's reason and event in `onValueChange`'s details.
- Call it in `onAttach` or before the person edits again, such as once you've read a file. Once the text has changed it inserts nothing and returns `false`; then insert with `actions.insert` at the caret, or drop the files.
- Text that comes with pasted or dropped files, usually their names, isn't inserted. A chip dragged within the prompt moves to where it is dropped, and never reaches `onAttach`.
- File drops need a `Field`: a Prompt outside one ignores dropped files. While files are dragged over it, Field renders `data-drag-over`: style a file drag over the field, or know a drop would land. A drop zone outside the composer, such as the whole conversation view, is yours: cancel `dragover` and `drop` there, and pass the files to `actions.attach()`. A drop on the field bubbles to it too, so skip a `drop` whose `defaultPrevented` is set: the composer took it.

The example's conversation view is such a drop zone: while files are dragged over it, it shows a scrim with a dashed outline and "Drop files to attach", under the pointer so a drop on the field still reaches the field.

```tsx from="./examples/hero/drop-zone.tsx"
onDrop={(event) => {
  depth.current = 0;
  setDragging(false);
  const files = [...event.dataTransfer.files];
  if (event.defaultPrevented || !files.length) return; // The composer took it, or no files.
  event.preventDefault();
  attach(files);
}}
```

The example has two Attach buttons, as [Controls](#controls) shows: one for files, and one with `capture` for the camera, shown only on a touch screen.

### Uploads

The upload is yours: start it in `onAttach` and keep its state in your own store, by the chip's `uploadId`, as [Chips](#chips) says. Read the file's address when the message is sent, as the example's `messageText` does, not in `toText`: Root calls `toText` only on an edit.

The composer checks no files: refuse types, sizes, counts and duplicates in `onAttach`, and say why in `Header`. `accept` limits only the picker; dropped and pasted files arrive whatever their type, so check types in `onAttach` too. Retrying a failed upload and cancelling one whose chip was removed are yours, as [Chips](#chips) says, and so is holding the message while uploads are pending. The example refuses files in `onAttach`, says why in `Header`, and starts an upload only for files that went into the text:

```tsx from="./examples/demo.tsx"
onAttach={(files, details) => {
  const accepted = files.filter(attachable);
  onNotice(
    accepted.length < files.length ? 'Only images and PDFs up to 20 MB can be attached.' : '',
  );
  const added = accepted.map((file) => {
    const chip = {
      kind: 'upload',
      id: crypto.randomUUID(),
      label: file.name,
      uploadId: crypto.randomUUID(),
    } as const;
    return {file, chip};
  });
  // Only files that went into the text start uploading.
  if (!details.insert(added.map(({chip}) => chip))) return;
  for (const {file, chip} of added) startUpload(chip.uploadId, file);
}}
```

Its upload chip reads its progress from that store and draws it with `Chip.Progress`; a progress tick renders only that chip. A file whose name starts with "fail" fails halfway: its chip turns negative and says why in its tooltip and in visually hidden text for screen readers, and `UploadErrors` says it in `Header`, for a touch screen. Removing a chip cancels its upload, and Undo starts it again, since `onValueChange` passes every value's upload ids to `syncUploads`:

```tsx from="./examples/hero/uploads.tsx"
export function syncUploads(uploadIds: readonly string[]) {
  for (const uploadId of requests.keys()) {
    if (uploadIds.includes(uploadId)) continue;
    clearInterval(requests.get(uploadId));
    requests.delete(uploadId);
    uploads.delete(uploadId);
    notify();
  }
  for (const uploadId of uploadIds) {
    const file = files.get(uploadId);
    if (file && !uploads.has(uploadId)) startUpload(uploadId, file);
  }
}
```

Its Send button is disabled until every file in the text is uploaded, and `onSubmit` checks as well, since Enter sends without Submit:

```tsx from="./examples/hero/uploads.tsx"
/**
 * Disabled until every file in the text is uploaded. Memoized: its parent renders again when the
 * prompt empties or fills, and the button needn't.
 */
export const SendButton = memo(function SendButton() {
  // Compared by `sameIds`, so typing doesn't render the button again.
  const uploadIds = Composer.useValue(uploadIdsOf, sameIds);
  const waiting = useSyncExternalStore(
    subscribe,
    () => pending(uploadIds),
    () => false,
  );
  return <Composer.Submit disabled={waiting} />;
});
```

## Chips

The value is a list of text and chips, each chip at least `{id, label}`. Draw a chip's content with [Chip](/components/chip/), `variant="soft"` and `density="compact"`, in Root's `renderChip`: a `Chip.Icon` and a `Chip.Label` for its place, `Chip.Separator`, and a `Chip.Label` for its name, as the example's `Upload › build-log.png` does. It is 20px tall in the prompt's 24px line and at most three quarters of the text's width; the name takes the ellipsis. `getChipDescription` tells screen readers what a chip is. `renderChip`, `chipDeletion` and `getChipDescription` take the chip, so each chip can differ.

Keep `renderChip` stable, at module scope or with `useCallback`: the chips draw again when it changes. The undo history keeps the chips as they were, so keep state that changes, such as an upload's progress or its failure, out of the chip. Give the chip an id of yours, such as `uploadId`, not its `id`: a copy gets a new `id`. Read the live state by it in `renderChip`, from a component that subscribes to it. To cancel an upload or start it again, compare the chips in `onValueChange`'s value with your uploads, as [Uploads](#uploads) shows: Undo brings a removed chip back.

In the prompt a chip is one character, and it goes as text does:

- Left or Right beside a chip selects it, and a second press moves the caret past it. Shift and an arrow extend the selection over it. A press or a tap on a chip in the focused prompt selects it; a tap beside it places the caret.
- Backspace and Delete remove a selected chip. Beside the caret, Backspace removes a chip whole by default; set `chipDeletion` to `select` to select it first, or to `revert` to turn it back into its `toText` text: Backspace beside the example's `build.mjs` gives `@scripts/build.mjs`, with the caret at its end, where [suggestions](#suggestions) open on it.
- A mouse or a pen drags a chip to another place in the text; it stays faint where it was until it is dropped. A finger doesn't drag: cut and paste move a chip there.
- Copied text is the `toText` text. Pasted back into the same prompt, its chips come back; after a cut, as the same chips.

Don't render `Chip.Remove` in `renderChip`: a person removes a chip with Backspace or Delete.

The example's chips are files, commands, uploads and long pastes. A pasted text is selected first, and a file turns back into its text:

```tsx from="./examples/hero/chips.tsx"
// A pasted text is costly to lose: the first Backspace selects it. A file turns back into its
// `@path`, where the suggestions open on it again.
export const chipDeletion = (chip: MessageChip) =>
  chip.kind === 'paste' ? 'select' : chip.kind === 'file' ? 'revert' : 'whole';
```

### Chip tooltips

The prompt doesn't show a chip's text on hover; wrap the chip in a [Tooltip](/components/tooltip/) in `renderChip`, with `Tooltip.Trigger render={<Chip.Root />}`, to say where it is or why its upload failed. Tooltips open for a pointer only, so on a touch screen say why an upload failed in a notice too. The example gives a file chip its path, a command its description, a failed upload its error, and a pasted text its first lines. Its `getChipDescription` says the path and the description too, so screen readers hear them. Root reads `getChipDescription` only when it draws a chip, so a failed upload says why in its own content, which follows your store:

```tsx from="./examples/hero/chips.tsx"
function TooltipChip({tooltip, semantic = 'neutral', children}: TooltipChipProps) {
  return (
    <Tooltip.Root>
      <Tooltip.Trigger render={<Chip.Root variant="soft" density="compact" semantic={semantic} />}>
        {children}
      </Tooltip.Trigger>
      <Tooltip.Portal>
        <Tooltip.Positioner>
          <Tooltip.Popup className={styles.lines}>{tooltip}</Tooltip.Popup>
        </Tooltip.Positioner>
      </Tooltip.Portal>
    </Tooltip.Root>
  );
}
```

```tsx from="./examples/hero/chips.tsx"
// What the tooltips show, for screen readers too: the tooltips open for a pointer only.
export const describeChip = (chip: MessageChip) => {
  switch (chip.kind) {
    case 'file':
      return `file, ${chip.path}`;
    case 'command':
      return `command, ${chip.description}`;
    case 'upload':
      return 'file';
    case 'paste':
      return 'pasted text';
  }
};
```

```tsx from="./examples/hero/chips.tsx"
const content = (
  <>
    <Chip.Icon>
      <UploadIcon />
    </Chip.Icon>
    <Chip.Label>Upload</Chip.Label>
    <Chip.Separator />
    <Chip.Label>{chip.label}</Chip.Label>
    {upload?.state === 'uploading' ? (
      <Chip.Progress value={upload.progress} aria-label={`Uploading ${chip.label}`} />
    ) : null}
    {upload?.state === 'failed' ? (
      // Here, not in `getChipDescription`: Root reads that only when it draws the chip, and a
      // failure doesn't draw it again.
      <span className={styles.visuallyHidden}>{`, ${upload.error}`}</span>
    ) : null}
  </>
);
```

## Long pastes

Root's `getPastedValue` receives pasted text and returns the value it goes in as, such as a chip for a long text that would fill the prompt; return `[text]` to keep it as text. The threshold is yours: the example makes a chip of more than ten lines, and its `toText` sends the text in its place. Undo right after such a paste gives the text as text, and a second Undo removes the paste. Cmd+Shift+V or Ctrl+Shift+V always pastes text as text. `getPastedValue` isn't called for files, which go to `onAttach`, for a copy from the same prompt, whose chips come back, or for text dropped on the prompt. Returning `[]` drops the paste.

```tsx from="./examples/hero/chips.tsx"
export const getPastedValue = (text: string): Message => {
  const lines = text.split('\n').length;
  if (lines <= MAX_LINES) return [text];
  return [{kind: 'paste', id: crypto.randomUUID(), label: `${lines} lines`, text}];
};
```

## Actions

`Composer.useActions()` gives the composer's actions to any part inside Root, such as a dictation button that inserts its text: `insert`, `focus`, `blur`, `submit`, `attach`, `undo`, `redo`, `clearHistory`, `getValue` and `atEdge`, which tells whether the caret is on the first or the last line, for keys of your own. `insert` goes where the caret was, also while the prompt isn't focused. The object never changes, so reading it doesn't render your part again. Root's `actionsRef` gets the same object, for code outside Root. `space` adds spaces around chips only, so text needs its own: the example's Dictate button adds its sentence at the end, where it knows the text before it, with a space after a word or a chip. Its drop zone passes files to `attach()`.

```tsx from="./examples/demo.tsx"
/** Whether a sentence added at the end needs a space first: after a word or a chip. */
const endsInWord = (value: Message) => {
  const last = value.at(-1);
  return last !== undefined && (Composer.isChip(last) || /\S$/.test(last));
};

function DictateButton() {
  const {insert, focus, getValue} = Composer.useActions<MessageChip>();
  return (
    <IconButton
      density="default"
      aria-label="Dictate"
      onClick={() => {
        // Demo only: a fixed sentence; insert the text your speech recognition hears. It goes at
        // the end, where the text before it is known: `space` spaces only around chips.
        const sentence = 'Summarize the open pull requests.';
        insert(endsInWord(getValue()) ? ` ${sentence}` : sentence, {at: 'end'});
        focus({at: 'end'});
      }}
    >
      <MicIcon />
    </IconButton>
  );
}
```

## Reading the value

`Composer.useValue(selector)` renders your part again only when what the selector returns changes. The selector runs on every edit: keep it cheap, and return a primitive or a stable reference, or pass `isEqual` as the second argument. To read the value once, in a handler, use `getValue()` from `useActions()`.

The example's secret notice returns a boolean, so it renders only when the answer changes; its Send button, in [Uploads](#uploads), compares the upload ids with `isEqual`. Other parts read it the same way, such as a token count that returns a number, or a hint for the command at the start that returns a string or `null`.

```tsx from="./examples/demo.tsx"
const hasSecret = (value: Message) => secret.test(toText(value));

function SecretNotice() {
  // A boolean: renders again only when the answer changes, not on every key.
  const found = Composer.useValue(hasSecret);
  return found ? <Text role="alert">This looks like a key or a password.</Text> : null;
}
```

## Suggestions

`Composer.useSuggestionMatch(triggers)` gives the trigger being typed before the caret and the query after it, such as `@` anywhere a word starts or `/` at the start. Find items for it and pass them to `Suggestions` as `results`, with the match they answer. In `onItemPick`, replace the match's range, such as with a chip through `insert`; undo then brings the typed text back. A trigger also matches its full-width form, such as `＠` for `@`, so there's no need to configure both. In Chinese and Japanese text a trigger also opens right after a character. Punctuation such as `,`, `"` or `、` ends the query, as whitespace does, and so does a closing bracket without a matching opener; `.`, `-`, `/` and `'` don't, so `@src/a.ts`, `@app/(marketing)/page.tsx` and `@O'Brien` stay one query.

The composer doesn't match, rank or load items: filter, sort and fetch them yourself, and debounce your requests if your source needs it. `onOpenChange` tells you when the list opens or closes, with a `reason` such as `escape-key`, `item-press` or `focus-out`, so you can cancel a request; `onItemHighlighted` tells you which item a person moved to, such as to preview it. While new results load, the previous ones for the same trigger stay in secondary text and can't be picked; Enter or Tab picks the first new item if it arrives within a second. After a second, `SuggestionPopup` renders `data-loading`. With no items, the popup opens only to show `SuggestionEmpty`. The list has no groups or separators; give each kind of item its own trigger.

The focus stays in the prompt. The arrow keys move through the list, skipping items with `disabled`, and Enter or Tab picks. While items show, Enter never submits, also while it waits for new results or every item is disabled; with only `SuggestionEmpty` up, Enter submits as usual. Tab with nothing to pick, or after a second's wait, moves the focus on. Escape closes the list, and it stays closed while typing goes on in that word, until a new trigger is typed. A tap picks when the finger lifts on an item. While an input method composes, its keys go to it, and a closed list doesn't open; an open one stays open, since Android keyboards compose nearly every word.

Escape calls `preventDefault()` when it closes the list. If you handle Escape on the page yourself, such as to stop a reply, listen in the bubbling phase on the document or the window and skip events whose `defaultPrevented` is set; a capturing listener runs before the list sees the key. Prompt's own `onKeyDown` runs first too: check whether the prompt has `data-popup-open`, which it renders while the popup shows.

`SuggestionStatus` tells screen readers how many suggestions there are once typing pauses, that nothing matches, or that results are loading; the keys to choose with are said once each time the list opens, where there is a keyboard. Keep it mounted inside `Suggestions`, outside the portal. It's visually hidden; to show it, give it a `className` that overrides its position, size and clipping, such as `position: static; inline-size: auto; block-size: auto; clip-path: none; white-space: normal`. Children as a function replace its text.

Use one `Suggestions` per Root: pass all your triggers to one `useSuggestionMatch` and branch on `match.character`, since a second `Suggestions` in the same Root throws. The list doesn't open while the prompt is disabled or read-only. Inside a [Modal](/components/modal/), pass the modal's popup element to `SuggestionPortal` as `container`.

The example's `@` searches files, with a request it cancels, and `/` filters commands, one of them disabled. A pick inserts a chip with a space around it:

```tsx from="./examples/hero/suggestions.tsx"
<Composer.Suggestions
  match={match}
  results={results}
  onItemPick={(item, picked, {event}) =>
    insert(chipOf(item), {at: picked.range, reason: 'item-press', event, space: true})
  }
  onOpenChange={(open) => {
    if (!open) request.current?.abort();
  }}
>
```

## Recalling messages

`Composer.useRecall(messages)` lets a person bring back what they sent before: ArrowUp on the prompt's first line shows the previous message, and ArrowDown on its last goes forward again, back to their draft after the newest. Pass the messages oldest first, as `onSubmit` received them, and the handler it returns to Prompt's `onKeyDown`. Call it in a component inside Root.

- The caret goes to the end of each message. In a message of several lines, or one that wraps, the arrows move through its lines first. Where a line wraps, the caret can show at the end of one line or at the start of the next, such as after Cmd+Right; there the first ArrowUp or ArrowDown moves the caret, and the second recalls.
- Editing a recalled message makes it the draft: the draft from before is gone, and the next ArrowUp starts again from the newest message.
- Going through messages is one undo step: Undo gives the draft back, and Redo the message. The recalled messages, and the draft coming back, reach `onValueChange` with reason `list-navigation`.
- Messages that equal the text are skipped, so a message sent twice in a row is one stop.
- A message comes back exactly as it was sent: no space is added around its chips.
- A recalled message opens no [suggestions](#suggestions), even when it ends in a trigger such as `/compact`, so ArrowUp goes on through it; once it's edited, the list may open again.
- Nothing is recalled while suggestions show, while an input method composes, while a chip is selected, or in a disabled or read-only prompt. Arrows with Shift, Alt, Ctrl or Cmd keep their usual meaning.
- Set `from: 'empty'` to start only from an empty prompt.

The composer doesn't keep the messages: store what was sent yourself, one list per conversation if you have several, and choose how many to keep. Switching `historyKey` ends a recall, and the message shown stays that draft. To handle other keys in `onKeyDown` too, call the handler from your own; it skips keys you called `preventDefault()` on. For an ArrowUp of your own, such as editing the last message, check `atEdge('up')` from `useActions()` instead, and skip the key while suggestions show, which `event.currentTarget.hasAttribute('data-popup-open')` tells.

In the example, ArrowUp brings back the conversation's messages:

```tsx from="./examples/demo.tsx"
/** Inside Root, where `useRecall` finds the prompt. */
function MessagePrompt({messages}: {messages: readonly Message[]}) {
  const recall = Composer.useRecall(messages);
  return (
    <Composer.Prompt
      aria-label="Message"
      placeholder="Write a message, @ for a file, / for a command…"
      onKeyDown={recall}
    />
  );
}
```

## Controls

`Controls` lays out its children in a row, in DOM order, so the order on screen is the order of focus; it places nothing. Put spacing and placement on a wrapper, such as a [Stack](/components/stack/) with `gap="auto"` or `justify-content`. The example puts the Attach buttons at the start, and Dictate and Send or Stop at the end:

```tsx from="./examples/demo.tsx"
<Composer.Controls render={<Stack direction="row" gap="auto" align="center" />}>
  <Stack direction="row" gap="xSmall" align="center">
    <Composer.Attach aria-label="Attach files" accept="image/*,.pdf" />
    <Composer.Attach
      aria-label="Take a photo"
      accept="image/*"
      capture="environment"
      className={styles.camera}
    >
      <PhotoCameraIcon />
    </Composer.Attach>
  </Stack>
  <Stack direction="row" gap="xSmall" align="center">
    <DictateButton />
    <SendOrStop replying={replying} onStop={stop} />
  </Stack>
</Composer.Controls>
```

## Header

Put notices, errors about the last message, and the message being replied to in `Header`. It stacks its children with a gap. Header is as wide as the frame and moves with the frame when Panel is hung; its content isn't aligned to the text inset. The example's Header warns about a key in the text, says why uploads failed, and says why files were refused:

```tsx from="./examples/demo.tsx"
<Composer.Header>
```

## Footer

Put your own controls and figures in `Footer`, such as a ghost [Dropdown](/components/dropdown/) trigger for the model and, at the end, a row of figures: a [Meter](/components/meter/) laid out inline for the context used, and `span`s for the rest. The row sets `margin-inline-start: auto` to sit at the end, and tertiary text on its own class, which the meter's value inherits; the controls keep their default size. Footer sets no text style, so these choices are yours.

Without a hang, the footer's controls put their text 2px inside the frame, which suits ghost controls: their hover fill reaches past it. With a hang, they put it on the hang, as in the example in a window 48rem wide or wider, where the model picker's text lines up with the prompt's. Its footer holds the ghost picker and the figures:

```tsx from="./examples/demo.tsx"
<Composer.Footer>
  <ModelPicker />
  <Figures />
</Composer.Footer>
```

For filled controls, such as a default Dropdown trigger, set `--composer-footer-inset` in a class on `Composer.Panel` or `Composer.Footer`, so their fill sits flush with the frame:

```css from="./examples/composer.module.css"
.filledControls {
  --composer-footer-inset: var(--semantic-dimension-space-control-padding-inline-small);
}
```

### Narrow

In a composer 40rem wide or narrower, the footer stays on one line: its children shrink and cut their text with an ellipsis. Give a child that must stay whole, such as the figures, `flex: none`. The footer then sets no gap of its own: controls are spaced by their padding. Children without padding of their own, such as plain text, need a gap you set; override the footer's with a class. It follows the composer's width, not the window's. A hung composer's container includes the hang, so it reaches 40rem about 2 × `--composer-text-inset` later.

<Demo example="./examples/narrow.tsx" />

### Your own breakpoints

Use the `composer` container to change the footer at widths of your own, such as hiding the cache figure in a narrow composer, as the narrow example does. You could also let the footer wrap instead, with `flex-wrap: wrap`.

```css from="./examples/composer.module.css"
@container composer (inline-size <= 30rem) {
  .cache {
    display: none;
  }
}
```

## Alignment

```css from="./examples/composer.module.css"
@media (min-width: 48rem) {
  .textAligned {
    --composer-hang: var(--composer-text-inset);
  }
}
```

Set it on `Composer.Panel` itself (via `className`): the inset is set on Panel, so a wrapper can't read it. Hang the frame only where there's room, `--composer-text-inset` at each side, such as inside `@media (min-width: …)` or a parent's container query; Panel is the `composer` container itself, so `@container composer` can't style it.

By default the frame lines up with the content around it. `--composer-hang` hangs the Panel out of its container by that much; set to `--composer-text-inset`, the distance from the frame's edge to the text, it lines up the prompt's text and the footer's with the content around it. A composer rendered by code you don't control can only be hung if that code passes your `className` through. In a wide window, the example's prompt text lines up with the messages above it.

## In a field

Inside a [Field](/components/field/), the prompt is the field's control: `Field.Label` names it, and the field's states and errors apply to it. Show an error with `Field.Error`: the composer doesn't mark validity on its own, but Field and Prompt render the field's `data-valid` or `data-invalid` for your own styles. A native label can't focus the prompt, so render the label as `Field.Label nativeLabel={false} render={<span />}`; a click on it then focuses the prompt. Set `required` on Root, and `name` on Root or `Field.Root`: a form submits the `toText` text, and a form reset returns to `defaultValue`. Without `onSubmit`, Enter and Submit submit the form, which validates first.

## In a form

Pass `render={<form />}` to Panel to make it a form. Submit then submits it, and its submit event calls Root's `onSubmit` with the event in the details; Enter calls it with the key event.

```tsx
<Composer.Root toText={toText} onSubmit={(message, {event}) => send(message, event)}>
  <Composer.Panel render={<form />}>
    <Composer.Field>
      <Composer.Prompt aria-label="Message" />
      <Composer.Controls>
        <Composer.Submit />
      </Composer.Controls>
    </Composer.Field>
  </Composer.Panel>
</Composer.Root>
```

## Your own state

Pass `value` and `onValueChange` to Root to keep the prompt elsewhere, such as one draft per conversation. `onValueChange` receives Base UI's change details, with the chips the change removed; `details.cancel()` refuses the change. Set `historyKey` to the draft's key, so each draft keeps its own undo. After sending, call `clearHistory()`, so undo can't bring the sent message back.

When the value comes from a store, subscribe in a small component that renders Root and takes the rest of the composer as `children`. Typing then renders only that component and the prompt, not the buttons or the footer; the example's `MessageComposer` is one. Define `renderChip` outside that component, or memoize it: a new function on every render draws every chip again.

## Disabled and read-only

`disabled` on Root disables the prompt, Attach and Submit. `readOnly` keeps the text focusable and copyable but not editable, and doesn't raise a phone's keyboard. Panel, Field and Prompt render `data-disabled`, `data-readonly` and `data-empty`, for your own styles.
